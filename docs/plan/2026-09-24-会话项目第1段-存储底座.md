# 会话项目第 1 段：存储底座与数据库化（09-24）

总计划见 `~/Documents/MiyuPlan/2026-09-24-work-plan.md` 第二节第 2 小节，施工单见同目录的 `2026-09-24-session-project-stage1.md`。
分支 `worktree-session-project-2026-09-24`，从 main a019596b 开。turns.rs 的拆分在这之前由另一个会话做完了（a019596b）。

## 改了什么

### 开库：客户端不体检，进程内共用一个连接（`conversation_db/open.rs`）

- **改之前**：每次 `StateStore::new` 都会：
  - 跑 6 条 PRAGMA；
  - `quick_check`，把整个文件扫一遍；
  - 查迁移；
  - 空闲页够多时跑 `incremental_vacuum`。
- 终端启动要开 6 次库，换一次会话 3 次，每轮对话 3 次。
- **按角色区分**：
  - 守护进程开主库（`open_maintained`）、开成员库（`open_member`）时照旧做维护；
  - 其余开库都是客户端。库已是当前版本就只跑 PRAGMA；库落后于程序时谁开谁迁移，迁移前的体检和备份照旧。
- **进程内共用**：按库文件路径缓存 `Weak<ConversationDb>`，同时核对 (dev, inode)，库文件被换掉就重开。维护每个连接只做一次。
- 开库代码从 `mod.rs` 整段搬进 `open.rs`，`mod.rs` 从 1143 行降到 700 行以内。

### 按页查询（`conversation_db/pages.rs`）

- `load_turn_page`：网页一页回合，不带 `context_messages`。在固定列序里用 `'[]'` 顶位，`map_turn_row` 不动。
- `session_replay_page`：回放快照翻页。`session_replay` 改成它的第一页。
- `user_inputs`：上键历史只取用户原话，口径同 `load_conversation` 里 role=user 的那几条，替换了 `editor.rs` 里的整段读取。
- 网页和全屏的翻页在第 2 段接上。

### 会话级零碎状态入库

- **命名迁移**（`migrations/named.rs`）：只加表，不动 `user_version`，所以老版本程序照样能开库，分支之间也不撞号。AGENTS.md §3.1 已补上这条规矩。
- **新表**，都挂在 sessions 上级联删除：
  - `session_values`：待办、提示词指纹、思考档位钉；
  - `repl_history`：上键历史，每会话留 200 条；
  - `legacy_file_imports`：记哪些老文件导过了。
- **老文件**：
  - 按会话在第一次读写前导进来，和导入标记放在同一个事务里，这样老内容排在新写入前面；
  - 本版保留；清空、删会话时一并删掉。
- **按账号选库**：
  - 待办工具用 goal 的口径（`tools/session_store.rs`），成员开他自己的库；
  - 网页那边用 `stores.for_session`；
  - 思考档位钉的 `ThinkingVariantScope::Session` 必须带上会话所在的库，类型上逼着调用方选对。

### 删会话一并清理

- `StateStore::delete_session` 会连带删除：
  - 老文件；
  - `spill/<会话>/`、`compact/<会话>/`，只在会话 id 原样就是合法目录名时删，防止截断撞名、防止 `.`；
  - artifact 目录（原有）。
- ask 会话、子代理会话的批量清理（`conversation_db/sweep.rs`）改成返回删掉的 id，同样清文件。以前只删行。

### 用量入库：机器级独立库 `state/usage.db`（`state/usage/`）

- 用量是所有账号共用的，账号靠 `acct` 列区分；会话库按账号分，所以用量单独一个库，照账本 `LedgerDb` 的样子单连接加 Mutex。
- 累计存一行 JSON（`usage_totals`），读、改、写在一个 IMMEDIATE 事务里，所以跨进程也不会互相覆盖。以前只有进程内锁。
- 老文件的导入：
  - `usage.json` 只导一次；
  - `usage-history.jsonl` 按字节偏移续导，回退到老版本后追加的行再升级时也补得上；
  - 坏行跳过，没写完的行留到下次；
  - 清空明细时连老文件一起删，偏移归零。
- 统计代码原样搬进 `usage/stats.rs`，只把「读文件」换成「查库」。明细列表的来源、模型、账号筛选和排序进了 SQL，同一秒的几条仍按写入先后排，和以前的稳定排序一致。

## 实测

量尺都在仓库里，标 `#[ignore]`。库文件是真库用只读连接 backup 出来的副本（页原样照搬，空闲页也在）。

| 项目 | 构建 | 改前 | 改后 |
| --- | --- | --- | --- |
| 终端启动开 6 次库（38.5 MB 的库） | debug | 118.9 ms | 7.4 ms |
| 同上 | release | 85.4 ms | 6.9 ms |
| 记一笔用量累计（btrfs） | debug | 2.08 ms | 0.05 ms |
| 同上 | release | 3.61 ms | 0.01 ms |
| 用量统计，14,511 条（本机 5.7 天的量） | debug | 93.4 ms | 69.7 ms |
| 同上，76,000 条（约 1 个月） | debug | 501.6 ms | 356.2 ms |
| 同上，14,511 条 | release | 12.2 ms | 12.7 ms |
| 同上，930,000 条（约 1 年） | release | 1157.7 ms | 815.7 ms |

几点说明：

- 统计查询在 release 下基本没变，大头是汇总本身。用量入库省下的主要是写：以前每调一次模型都要把 usage.json 读出来、改、fsync、改名，缓存保活、QQ 每条消息的判官都算。
- 老账本第一次开库时要导一次：release 下 14,511 条约 68 ms，一年量约 5 秒。之后不再导。
- 另外两处快了多少没单独量：
  - 上键历史：为了几十 KB 原话读几 MB 整段对话 → 只查原话；
  - 网页翻页：第 2 段接上后才生效。

## 口径（我定的，报告里单列）

1. 用量放独立库 `state/usage.db`，不放会话库：它是机器级的，放进按账号分的会话库，成员的用量会散在各家。
2. 全局的 `thinking-variants.json` 不入库，它是偏好，算配置。`relay/sessions.json` 不入库，它是跨账号的全局映射，成员会话不在管理员库里，挂不上外键。
3. 删会话清 spill、compact 目录，只在会话 id 原样就是合法目录名时删。
4. 老文件本版保留。清空待办、清空明细、删会话时一并删。
5. 统计查询不按时间窗预筛：`first_ts` 要看全部记录，一年的日历热图也要 364 天。保持原口径。

## 顺手发现、没做的

- `AppConfig::load` 每次都把整份 models.dev 目录装进内存，⑤ 的报告里也提过：守护进程里任务唤醒、生图、IPC 重载配置都会走到它，装一次之后目录就一直是全的。
- 导入导出（`engine/transfer`）没带 `todos/`、`repl-history/`、`usage-history.jsonl` 这些老文件；入库之后它们跟着会话库和 `usage.db` 走。export 的注册表没登记 `usage.db`，要不要带上待定。
- `transfer/fixups.rs` 只开 `state_dir/conversation.db`，家目录布局下库在 `home/<管理员>/`，fixups 可能空转。调研时看到，没核实。
