来源：opencode v2 调研 3.5 第 3、4 条（工作安排第二节第 4 小节「之后可选」，对应待办「优化内存占用」）。
分支 `worktree-finalize-events-2026-09-25`，从集成分支 `worktree-integration-2026-09-25`（72544dec）开。

## 一、回合收尾一个事务

### 改之前
收尾分五笔写（`turn_loop/stream.rs`、`turn_loop/redo.rs`）：持久上下文 → 完成标记（同一笔里删掉流水）→ 上下文
锚点 → 输出速度 → 最终工具流。完成那一笔之后的任何一笔失败，或进程在两笔之间死掉，库里就留下「已完成、流水
已删、工具流还是上一个检查点」的轮；回合本身照样报错，人看到失败，库里记的却是完成。

### 做法
- `miyu_core::state::{TurnCompletion, TurnFinishExtras}`：完成字段与收尾时要一起写的几样（锚点照写、速度
  有才写、工具流给了才写、持久上下文追加）。
- `ConversationDb::finish_turn` / `finish_turn_revision`：原来两个完成方法的事务里，在提交前补写 extras。
  老方法 `complete_turn_with_usage` / `complete_turn_revision_with_usage` 签名不动，转调新方法、不带 extras，
  测试与别处调用点零改动。
- 引擎两处收尾改成一次 `guard.finish(&completion, &extras)`；工具流改在完成之前派生（纯派生，顺序无关）。
  失败时守卫照旧在 Drop 里把这一轮收成已中断，流水留着。
- 各列的写法与原来分开写的 `set_turn_context_end` / `set_turn_generation` / `set_turn_tool_flow` /
  `append_tool_reports` 一致：普通回合没有工具轮时不写工具流，重做无条件写（旧修订的工具流必须盖掉）。

### 验证
- `agent::tests::turn_finish::a_failed_finish_does_not_leave_a_completed_turn_behind`：库里装一个触发器，
  让「已完成的轮再改工具流」失败。修前回合报错、库里却是 completed；修后整笔回滚、这一轮收成已中断，
  检查点那份工具流还在。退回修复前报红。
- `state::tests::turns`：`finish_turn` 一次写齐五样；收尾中途失败整笔回滚（还是 running、流水在、
  工具流是检查点那份、持久上下文一条没进）。

## 二、事件载荷共享

### 改之前
- `EventHub::publish` 序列化一次，但每个订阅者 `recv` 拿到的是整条记录的拷贝（kind 和 JSON 正文各一份
  `String`），重放缓冲里再存一份。
- 七处订阅者（网页 SSE 的归属过滤、终端跟随、IPC 回合、平台回合、goal 驱动、后台任务唤醒、子代理宿主）为了
  看一眼这条事件是哪一轮、哪个会话，把每条事件的 JSON 整条解析一遍——包括别的会话刷屏的那些。

### 做法
- 广播与重放缓冲里存 `SharedEvent = Arc<EventRecord>`：缓冲、广播、每个订阅者手里是同一份。
- `EventRecord` 加 `run_id` / `session_id` 两个路由字段，发布时从正文里取好。
- 订阅者先看路由字段，是自己那一轮才解析正文；归属过滤只有「会话排序」广播还要看正文里的 id 列表；
  goal 驱动与子代理宿主的会话判断直接读字段。
- 事件的字节与语义不变：SSE、IPC 帧发出去的 kind / data 逐字节相同。

### 验证
- `web::tests::events_questions`：路由字段、缓冲与订阅者共享同一份记录（`Arc::ptr_eq`）。
- 量尺 `event_fanout_cost_scale`（`--ignored`）：数字见下。

## 实测
- 退回修复前报红：把引擎收尾改回「先完成、再单独写工具流」，`turn_finish` 那条报
  `a failed finish must not leave the turn marked completed`；还原后全绿。
- 量尺 `event_fanout_cost_scale`（debug 构建，同一进程里两种口径各跑一遍，三次）：4000 条事件、2.7 MB JSON 正文、
  6 个订阅者、自己那一轮占六分之一——

  | | 耗时 | 为订阅者拷贝的正文 |
  |---|---|---|
  | 旧口径（每条拷一份、整条解析再看 run_id） | 109–123 ms | 16.2 MB |
  | 新口径（共享一份、先看路由字段） | 29–35 ms | 0 |
  | 倍率 | 3.6–3.8× | — |

  拷贝是瞬时分配，抬的是流式高峰时的 RSS；解析省下的是别的会话刷屏时各订阅者白做的功。
- `refactor-check.sh` 五道全绿，用例 2987 → 2992；层序门禁通过。
