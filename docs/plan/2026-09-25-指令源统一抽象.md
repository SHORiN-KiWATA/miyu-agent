B13 所在）开出。

## 一、统一接口（第 1 步，字节零变化）
- 模型得知道「此刻是什么样」的事，原来各写一套「跟最近一份比、变了才发」：runtime、sandbox 在
  `chat_messages` 里各一段，插话合并时 runtime 再写一遍，网页 artifact 清单快照在 `assemble_turn_tail`
  里又一套。
- 现在收成 `agent/instruction_source.rs`：
  - `InstructionSource`：`tag`（块的开头）、`latest`（请求里模型最近看到的那一份，默认按整条消息的开头认，
    快照按标签在正文里找）、`current`（此刻的完整块，`None` = 此刻没有）、`gone`（没了时补的那一句，默认不补）。
  - `project`：一样不发、变了发整份、没了补一句且只补一次。规矩只写这一遍。
  - `push_projected`：按源的顺序追加，顺序即缓存前缀，新源只往后加。
  - 「模型最近看到的是什么」直接从请求里读，不另记状态：带着它的那一轮被压缩折进摘要、被裁剪掉以后，
    请求里看不到了，下一轮自然整份重发。
- 三处改走它：`RuntimeSource`、`SandboxSource`（受众判据挪进 `SandboxSource::applies`）、`HostSnapshot`
  （场所递进来的状态快照，`STATE_SNAPSHOT_TAGS` 与 `latest_visible_snapshot` 挪进来）。
- 不收的：联想记忆（按行去重，是「一组条目只发没见过的」，不是「此刻的状态」）、人格提醒（按间隔）、
  `[SystemInfo:` 常驻告示（整段在请求里任何位置出现过就不发）。三者语义不同，硬塞进来只会多一层分支。
- 验证：`request_shape_probe` 加上这一轮真发出去的工具定义全文，另加两张沙盒脸（开着时第一次说、说过之后
  关了补一句）；改动前后七张脸逐字节相同。投影规矩单测 3 条。

## 二、技能目录迁成指令源（第 2 步）
- 用户拍板：整份搬出 `load_skill` 描述，放进回合尾巴（opencode / Claude Code 的做法）。另两个选项
  （留在描述里按会话冻结 + 另发变化说明；只补 B13 的漏洞）没选。
- 做法：
  - `load_skill` 描述改成常量，真相源回到 `descriptions/load_skill.json`（`spec.rs` 里那个例外删掉）。
    描述里那句「必须是下面列出的技能之一」改成指向最新的 `<available-skills>` 块，别的字不动。
  - 注册表存目录块（`skill_catalog()`，没有技能是 None），热刷新只换这一块，不再重新注册工具。
  - `SkillsSource`：块是 `<available-skills>` + 每件一行（格式沿用原来描述里那份）；一件不剩时补
    `<available-skills/>`。只在这一轮的工具面里有 `load_skill` 时发（工具关着、子代理会话、单轮白名单
    没放行都不发）。排在 runtime、sandbox 之后。
  - 回合开始先按指纹刷一次目录再拼尾巴（常驻 REPL 的 Agent 也拿得到此刻的目录）；redo 同样。
  - B13 的按会话冻结连同 `app_state` 里的 `skill_catalog:<会话>` 快照、重置与删会话时的清理一起撤掉。
    09-25 复查出的漏洞（stub 模式没冻结、压缩请求与上下文估算用没冻结的那份、模型不知道目录变了）
    随之不存在：描述在哪都是同一份常量，目录变了下一轮就发新的。
  - `manage_skill` 发布、删除的回执 `catalog_refresh` 从 `next tool round` 改成 `next turn`（照实说）。
- 字节变化（`request_shape_probe` 对比）：dev 脸零变化；其余六张脸只动两处——`load_skill` 描述去掉目录、
  回合尾巴末尾多一条 `<available-skills>`。system 提示词、历史、别的工具都不变。上线时所有会话一次性冷启动
  （tools 变了一次），之后 tools 在所有会话里是同一份常量，技能增删不再打断任何会话的缓存。
- 顺手修的（用户批「顺手修」）：`manage_skill` 回执里的 `apply_patch` / `publish_skill`、skill-creator 正文里的
  `apply_patch` 都是已经不存在的工具名，改成 `edit` 与 `manage_skill action=publish`。

## 三、已知局限
- 回合中途溢出触发压缩重试（`overflow_recovery`）时，重建的前缀只接回这一轮原来的尾巴：目录那份化石若在被
  折掉的轮里，这一轮剩下的请求看不到目录（`load_skill` 照样能按名字加载），下一轮自动重发。runtime、sandbox
  原来就是这样。溢出恢复在分支 ① 里改过，这里不动，集成时再看要不要补。
- 插话合并时只补 runtime，沙盒与技能目录的变化等下一轮再说（和原来一样）。
- stub 模式下 `load_tools` 描述里的 `<unregistered_scripts>` 清单、脚本工具的热插拔仍会改 tools 字节
  （08-17 起已知，这次不在范围里）。

## 四、验证
- 新用例（退回 B13 做法时报红）：`the_skill_catalog_rides_the_turn_tail_and_the_tools_never_change`——五轮里
  tools 逐字节不变；第一轮尾巴带目录；中途加一件技能，下一轮发新的整份、老的那份照旧回放；目录没变不重发；
  压缩后重发；技能删光补空目录。
- skills 单测：目录块含内置 skill-creator；没有技能时没有目录块；`load_skill` 两档描述都是同一份常量、不带清单。
- 夹具 `registry-shapes.json` 只有 `load_skill` 一项的哈希变了。
