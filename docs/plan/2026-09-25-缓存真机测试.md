# 缓存真机测试与 QQ 工具表（09-25）

来源：用户「为什么缓存效果我感觉不好」，给 1000 万 token 预算，用 opencodego 的 deepseek-v4.1-flash
测复杂场景，期望轮内 99.5+、跨轮 99+。分支 `worktree-cache-live-2026-09-25`，从集成分支 9fc063e1 开。
实际用掉 507 万 prompt token。

## 两个口径
- **命中率** = cache_read / prompt。footer 上的 C% 就是它（会话树累计）。每一步新追加的内容（工具输出、
  子代理报告）不可能在缓存里，所以天然只有 86–96%。
- **前缀覆盖率** = cache_read / 同一会话上一个请求的 prompt：上一次已经发过的内容，这次有多少吃到了缓存。
  这才是「缓存有没有被我们掰断」的尺子。

## 实测
| 来源 | 分组 | 命中率 | 前缀覆盖率 |
|---|---|---|---|
| 复杂场景主会话 | 轮内（16） | 95.76% | 99.74% |
| 复杂场景主会话 | 跨轮（11），去掉压缩后那一跳 | 98.54% | 99.72% |
| 复杂场景子代理 | 轮内 | 95.5–96.4% | 99.37–99.45% |
| 真实日志 09-24 回放修复之后 | 轮内（221） | 94.91% | 99.63% |
| 真实日志 09-24 回放修复之后 | 跨轮（23） | 69.38% | 70.15% |

复杂场景覆盖了：多轮工具、同一回复里并行 4 个工具、前台/后台子代理、回合中插话、打断后接着说、中途加技能、
`/compact`（fork 式）、记忆开着、开发模式会话。用户截图里的 `Σ760.2k(C81%)` 按同一段日志复算是 81.2%，
同一段的轮内覆盖率是 99.84%。

供应商侧直连探针（每项至少 3 次）：
- `x-opencode-request` 每请求换还是一轮一个：99.72% vs 99.76%，没有差别；
- 新内容进缓存几乎是即时的（隔 0/1/3 秒都 ≥99.4%）；
- 同一冷前缀并发几路互相吃不到（12 次里 9 次读到 0），第一波跑完之后全都盖满；缓存跨会话共享；
- 缓存读按 128 token 取整，每条请求天然最多丢 127；
- 空闲 30 分钟内没有被逐出；
- 上一轮的思考原样回传（现状）跨轮 99.7%，是最优的做法。

## 真实跨轮缺口的根因
按分量排：
1. **我方，大头**：`send_qq_message`、`qq_contacts` 只在 NapCat 连上时注册，daemon 重启、QQ 重连时工具表
   就变，所有开着的会话下一次请求整条前缀作废（09-25 08:49 一次 23.7 万）。
2. 供应商偶发整条冷掉，像是换了机器，客户端修不了。
3. 按设计的：压缩后第一跳、终端与网页提示词不同。
4. 并行子代理同时起跑，公共前缀各冷算一遍（约 1 万 token 每个，收益太小，不做）。

## 做法（用户拍板 A）
配置里开了 QQ 就恒在工具表里，掉线在调用时拦：`send_qq_message` / `qq_contacts` 调用时端口没连上，
回一句「QQ is not connected right now (NapCat is offline); nothing was sent」。改了四处：
`builtin_plugins::reg_platform_outreach`（本地会话）、`platforms::tool::register_outreach`（平台会话，去掉
`connected` 参数）、`TurnResourceCache::key`（连接位不再进键）、`platform_outreach` 的发送与地址簿。
这推翻了 09-18「掉线时模型看不到它」的设计。

## footer：C% 不动，加「断缓存」计数（用户拍板）
先调研了别家（dsh、opencode、codex、Claude Code、cline、aider、Gemini CLI，读到源码行号/官方文档）：
opencode、codex、cline、aider 根本不显示缓存百分比，只列读写 token 数和费用；显示百分比的 dsh 网页、
Claude Code、Gemini 都是「累计缓存读 ÷ 累计输入」这一类，和 Miyu 的 C% 同类。只有 Claude Code 有前缀
覆盖式的判定，但不显示比例，只在 `/usage` 里报「断缓存」次数、最近一次、重写了多少、可能原因。

照它的判法做（`llm/cache_break.rs`）：
- 本来能读到的量 = min(上一请求完整 prompt, 本次完整 prompt)；本次缓存读不到它的 95%、且缺口 ≥ 2000
  token，记一次；
- 原因按前缀差异归：系统提示词变了 / 工具表变了（带 `tools_diff`）/ 历史第几条被改写 / 我方一字未改、
  供应商没接住（空闲超过 5 分钟的写上隔了多久）；
- 压缩成功后的下一次请求是预期重建，不记（`Compactor` 成功时 `note_cache_rebuild`）；
- 只判主对话与子代理的请求（作用域 `chat`），供应商不报缓存用量的不判；进程里没有上一请求可比的是
  冷启动，不记。

落库：命名迁移 `2026-09-25-cache-breaks` 加 `cache_breaks` 表（挂会话级联删除），引擎每次请求后取走
落库，会话树（主会话 + 子代理）的次数随 `RoundUsage` / `chat.round_usage` 与会话快照
（`SessionState.cache_breaks`）带给客户端。footer：`Σ760.2k(C81%·断2)`，没断过不挂；`/usage`
列最近 10 次的时间、重算量、原因。网页这一版没做。

## 验证
- 断缓存：`llm::cache_break` 单测 5 条（冷启动与小缺口不记、纯追加归供应商、三种我方改写、压缩后预期
  重建只豁免一次、旁路与不报缓存的不判）；`state::tests::cache_breaks`（按会话树计数、新的在前、删会话
  连记录一起走）；`render::tests::usage::cache_breaks_ride_behind_the_cache_rate`；IPC 解码带上次数；
- `platform_outreach::tests::send_routes_through_the_outreach_port` 末尾加「掉线」三问（旧代码照发，报红）；
- `web::tests::session::terminal_outreach_stays_on_the_tool_face_while_qq_is_offline`（旧代码没这件工具，报红）；
- `platform_outreach_tools_go_to_everyone_whether_or_not_qq_is_connected`（原「没连着不装」那条按新语义改）；
- `request_shape_probe` 改前改后逐字节一致（这五张脸不开 QQ）。

## 顺带发现（没做）
走 antigravity 的 QQ 群会话，工具表每隔一轮在整套与精简之间翻一次（`7514…` ↔ `af9e…`），每翻一次前缀
整条作废；antigravity 几乎不报缓存读，日志里看不出损失。值得单独立项查。
