# 溢出后的压缩重试从没成功过；429 / 额度 / 超长的重试不对（09-24）

对照 opencode v2 时查出的两处（调研 B1、B6，`~/Documents/MiyuPlan/2026-09-24-opencode-v2-deep-study.md`）。

## B1 溢出后「压缩一次再重试」必败

**现象**：模型报上下文超长时，本该压缩一次再重试，实际直接把错误抛给用户。终端和网页显示报错，QQ 里那一轮不回话。

**根因**：
- 回合一开始就在库里写一行 `status='running'` 的记录（`conversation_db/turns.rs` 的 `start_turn`）。
- 被动兜底（`turn_loop/overflow_recovery.rs`）调 `Compactor::perform_compact`，它读全部可见回合，见到 running 就 `bail!("cannot compact while another conversation turn is running")`。
- 兜底恰好发生在自己这一轮里，所以每次都走到 `compact-and-retry failed`。组上下文那边用的是排除当前轮的 `load_visible_turns_excluding`，只有压缩这里漏了。
- 这道拦截 07-16 就在（b4b69ec5），兜底 08-06 才加（f83e9d63），之后没有任何测试覆盖这条路。

**修法**：`Compactor::excluding_running_turn(当前轮)`。这一轮不参与折叠、也不算进保留的尾巴；落库前「会话没变」的核对仍然算上它，别的 running 轮照样拒绝。

## B6 429 / 额度 / 超长的重试

**根因**：
- HTTP 层只重试 5xx，响应头全丢；全库没有 Retry-After 解析。429 一律冷却 600 秒，同一端点不再试：单端点用户碰上几秒的节流，整轮直接失败。
- 超长（`context_length`、`context_window`、`max_tokens`）被归成「端点不兼容」：不冷却，还允许同端点重打。单端点会被补齐打三次、每次隔 2 秒，之后才轮到（本就失效的）被动压缩。
- 402 没有专门处理。报文把 code 写成 `invalid_request_error` 时，会被当成「请求本身被拒」，连换端点都不试。

**修法**（`llm/openai_compatible/errors.rs`、`endpoints.rs`、`chat.rs`）：
- 新增两档失败：
  - `ContextOverflow`：4xx 报文命中 `is_context_overflow_message`，或报文里有 `context_length_exceeded` 一类的码。不冷却，同一端点不重打，可以换端点（别家窗口可能更大）。
  - `Quota`：402，以及 `insufficient_quota`、`insufficient_balance` 一类的报文。冷却 600 秒，同一端点不重打，可以换端点。
- `HttpStatusFailure` 带上 `retry_after`，从 `retry-after-ms` 和 `retry-after`（秒数或 HTTP 日期）读出。chat、Anthropic、Responses 三条失败路径都在读报文之前取头。
- 端点循环里，限流并且服务端给的等待不超过 20 秒、还没出字时，原地等完再打同一端点一次（`HONORED_RETRY_AFTER_MAX`）。限流的冷却改用服务端给的时长，夹在 30 到 600 秒之间；拿不到还是 600 秒。
- 所有端点都失败、其中有超长时，汇总错误是类型化的 `ContextOverflowed`。`is_context_overflow_error` 先认它，再按措辞兜底，不再依赖被裁到 120 字的报文里恰好有超长的字样。

## 验证
- 先红后绿：
  - `agent::tests::overflow_recovery::context_overflow_is_recovered_by_compacting_and_retrying`：修前错误原样抛出，同端点连打三次。
  - `failure_classes` 里三条：短 Retry-After 原地等、超长不重打、402 换端点。修前都红。
- 护栏：长 Retry-After 不等；Retry-After 三种写法的解析；两档新分类，包括限流报文里的「too many tokens」不会被误判成超长。
- openai_compatible 全部 173 条测试通过，五道门禁通过。
