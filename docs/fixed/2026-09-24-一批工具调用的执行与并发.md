# 一批工具调用的执行顺序、并发、图片插队与「准备xx」（09-24）

对照 opencode v2 时查出（调研 B7、B9、图片插队），加上用户点名的「同轮工具并发」，以及提问面板上方一直挂着「⠋ 准备问题」（goal_question 走查红的那一条）。设计依据见 `~/Documents/MiyuPlan/2026-09-24-opencode-v2-deep-study.md` 第二节。

## 同轮工具并发（新功能）
- **做法**：
  - `ToolSpec::concurrent()` 显式白名单：read、glob、grep、web_search、web_fetch、subagent。不按读写权限推断，原因有三：MCP 工具默认登记为只读，实际可能写东西；print_image 是只读，却要独占终端；脚本默认按写处理。
  - 一批里相邻的可并发调用（至少两个）编成一段，在调用顺序里原地执行；有复读跳过或提问的批次整批串行。
  - 执行拆成两段：
    - `execute_tool_call` 与 `run_concurrent_segment` 只负责跑。按 `tools.subagent_concurrency` 分波，全在同一个 task 里用 `poll_fn` 轮询，不 spawn——沙盒、工作目录、会话这些 task-local 出了 task 就拿不到，路径检查会直接放行。
    - `commit_tool_result` 按调用顺序逐个收尾：外溢、复读闸记账、内联媒体、load_tools 记账、推 tool 消息、足迹、结果事件、报告。
  - 结果事件在收尾时按调用顺序发，「开始调用」事件都在任何一条结果之前。给模型的顺序和字节与完成先后无关，和回放一致。
- **收益**：本机实测，按白名单只能省下全部工具耗时的 0.5% 左右。用户的原则是「没风险、有收益就做」。

## B9 并行子代理组的三个偏差（随上面一起消失）
- 子代理组原来在逐个执行的循环之前先跑，越过排在它前面的 edit、run_command；现在段在调用顺序里原地执行。
- 成败原来写死为成功，子代理失败返回的 `ok:false` 也画成成功；现在统一由 `commit_tool_result` 按 JSON 判定。
- 工具闸上下文原来传的是空的 `GuardCtx::default()`，也不记复读闸；现在传当前的 used_tools，复读闸照记。

## 图片消息插在工具结果中间
- **现象**（红用例坐实）：模型认图、但供应商不收工具结果里的图（`tool_result_media: false`）时，图片补成一条用户消息，紧跟在自己那条工具结果后面。一批 [look, noop] 实际发出去的是：`tool:call_0`、`tool:call_1`（配平检查补的占位）、`user`（图片）、`tool:call_1`（真结果又来一次）。严格的网关会 400。
- **修法**：`push_tool_result_with_media` 把伴随消息交给调用方攒着，整批工具结果推完再追加。活体与回放（`push_tool_flow`）都这样放，字节一致。
- **代价**：老回合里恰好是「多调用、带图的那条不在最后」的轮，回放顺序变了，那条会话冷启动一次。
- 现有用例 `inline_media_falls_back_to_a_user_message_when_the_provider_cannot_carry_it` 原来断言的就是旧的错误顺序，已经改成新顺序。

## B7 「准备xx」按分片计数
- **根因**：SSE 累加器只要这一片带着函数名就往外报一次；有的网关每一片都重发完整函数名，于是每片都算一个新调用，`tool_calls_seen` 第二片起就判成批量。
- **修法**：只在名字真的变了（第一次出现，或碎片续上）时才报。渲染层的「准备编辑」停留问题由 miyu-d7 另行修复（ecaa9b7b），这里只修计数。

## 提问面板上方挂着「⠋ 准备问题」
- **根因**：「准备问题」是转轮画的那一行。提问事件一到，`prepare_for_panel` 清掉了准备态但没重画；面板一开 tick 就停了，那一帧就一直挂在面板上方（`goal_question` 走查「没有卡在「准备问题」」一直红）。
- **修法**：`prepare_for_panel` 清掉准备态后，按新状态重设转轮文字并强制 tick 一次，随后 `apply_renderer_frame` 把新画面写上屏；「已思考」这类其它活动行照旧留着。
